# Extraction failure investigation

## What is established, and what is not

The supplied production symptom is POST `/api/extract-profile` → HTTP 502, `INVALID_AI_RESPONSE`, with “AI returned an invalid or incomplete response. No changes were saved.” The user confirmed that Worker version `bfb4dd5d-12c6-4e12-b3e6-69a4dd62031d` was deployed from clean Git commit `adf9589613a5e13c4e42a62415b8eeaa4086eb29` using `wrangler.same-origin.jsonc`. The failing request UUID was supplied, but provider completion metadata remains unknown. The tail showed only “POST /api/extract-profile - Ok” with no internal details. This workspace has no Cloudflare credentials or tool capable of reading this standalone Worker's production logs. **The particular production failure's root cause is therefore not established.** Nothing was deployed or submitted to the paid model during this investigation.

In the code matching that message, the same catch handled provider-envelope JSON parsing, a missing choice, non-stop finish reasons (including length), refusal, model-content JSON parsing, and Zod parsing. Both extraction and its independent factuality audit called that helper. This is a confirmed diagnostic defect: the error discarded the information needed to distinguish the actual failure stage.

For this code version, an OpenAI HTTP 400 (including a schema rejection) takes the earlier non-OK branch and returns `AI_UNAVAILABLE`, not the supplied message. An initial fetch failure before receiving a Response also takes that earlier branch; a failure while reading the response body after successful headers can still enter the shared response-processing catch. Cloudflare tail “Ok” describes a handled invocation and does not imply an HTTP 2xx API response or a successful upstream model call; a caught error returned as HTTP 502 can still be shown as Ok. The earlier METHOD_NOT_ALLOWED response is a separate method/routing outcome, not evidence for the POST failure. This is evidence against declaring an unsupported-schema HTTP rejection the root cause of this particular error. With the confirmed clean deployment commit, the reported error is attributable to that shared helper catch, but it still does not identify which later branch failed.

Synthetic regressions reproduce the supplied 502/code using malformed model JSON, structurally invalid profiles, invalid URLs and duplicate fact IDs, and also demonstrate how truncation/refusal previously entered the same catch. A completely valid first extraction followed by malformed audit output reproduces it as well. These are distinct demonstrated failure modes, not claims about the missing production response.

## Full request/data flow

1. `src/lib/documents.ts` extracts PDF or DOCX text locally, with file/page/expanded-archive/text limits. Pasted information skips file extraction. Failure here does not send the Worker request.
2. `Journal.propose` calls the existing request adapter in `src/main.tsx`. For an update, the adapter includes the existing approved profile as source context; document import sends extracted text. The typed client validates the bounded `{text}` input and POSTs JSON to relative `/api/extract-profile` using Access session credentials and refusing redirects. There is no PDF binary upload to the Worker.
3. `worker/index.ts` assigns a new server request UUID (ignoring any caller-supplied request ID). Existing Access JWT, origin, method, body-size, input-validation, timeout and rate-limit gates run first. The reported code is not a method error; a GET would be 405.
4. `worker/ai.ts` generates the provider JSON Schema, sends Chat Completions with strict Structured Outputs, `store:false`, the configured model and bounded completion tokens. Schema generation, network/non-OK provider responses, malformed response envelopes and response bodies are separate failure stages.
5. It checks refusal and finish reason **before parsing content**. `length` is `AI_INCOMPLETE` (502); refusal/content filtering is `AI_REFUSED` (422). Missing/malformed envelope, invalid content JSON and invalid Zod output remain `INVALID_AI_RESPONSE`, with a safe diagnostic phase. No partial result is accepted and no paid automatic retry is added.
6. A successful extracted draft undergoes a separate structured factuality-audit model call. Diagnostic operation `audit` distinguishes that call from `extract`; unsupported factual claims remain rejected. Audit reasons and refusal text are never logged or echoed.
7. Only after successful validation and audit does the Worker assign application metadata, bound missing-field warnings and validate the final response. The client validates the response again. A valid proposal is shown for review; only a separate apply/review/confirm/save operation writes an approved master profile to Dexie.
8. The client retains the safe server request ID on errors and shows a reference with the message, while keeping entered information and saved records unchanged. No model text is included in client error details.

## Schema and validation changes

Extraction and the final API response now share `extractResponseSchema` directly. The profile's `verified` field is an explicit false literal in this response (the full profile type remains unchanged). All original profile/fact/URL validation and duplicate-ID checks remain active.

The generated schema is locally checked against the strict Structured Outputs subset: an object root, every object property required, `additionalProperties:false`, supported types/keywords/formats, and nested anyOf/array/object shapes. Zod literals are rendered as equivalent enums; exclusive integer bounds are rendered as equivalent inclusive bounds. Unsupported dialect/URI format markers are removed as before. This prevents sending accidentally unsupported new schema constructs. Schema generation failures are separately diagnosed as `AI_SCHEMA_CONFIGURATION`.

The request schema and Zod parser share their shape and representable constraints. Custom semantic checks (public HTTPS URLs, duplicate/global fact IDs, factuality and evidence) remain additional local gates; Structured Outputs is not a proof of those properties. A malformed URL now produces a normal validation issue/path instead of throwing inside a refinement. No unsafe output is repaired into a valid profile or saved. The prompt now makes clear that model-supplied metadata must satisfy the schema even though the application replaces it.

Two independent consistency defects were confirmed and fixed: model warnings previously accepted whitespace that the final API schema rejected, and adding application missing-field warnings could exceed the final 50-warning limit. The single schema closes the former mismatch; bounded application-generated warnings fix the latter. These defects alone are not evidence for the production incident, whose supplied message was emitted earlier in the flow.

Reference: OpenAI's [Structured Outputs guide](https://platform.openai.com/docs/guides/structured-outputs). Tests inspect generated request schemas and mocked provider behavior; they do not prove live provider/model acceptance or reproduce the unavailable private production payload.

## Privacy-safe diagnostics and correlation

The Worker emits bounded JSON application events with server `requestId`, fixed endpoint/operation/phase/code, provider HTTP status, optional syntax-checked provider request/response IDs, a refusal boolean and an allowlisted finish reason. Zod failures include at most 12 issue code/path entries and a total count. Paths use only schema-defined field names; array indices become `[]` and unknown segments become `<field>`. The logger never serializes Zod error messages/objects, received values, unknown-key names, exceptions/stacks, input text, profile contents, audit reasons, refusal contents, model responses, authorization headers, identity emails, tokens or keys. Logging failures cannot bypass validation or change outcomes.

The response preserves the existing structured error envelope and `X-Request-ID`. The client accepts only UUID-shaped request IDs for display. Application diagnostics are emitted through `console.warn`; no observability setting, retention policy or Cloudflare configuration was changed. Existing `observability.enabled:false` means logs may not be retained; after a separately approved deployment, an authorized operator can capture the safe application events via live tail or an already configured log sink. Do not share raw platform request events, headers or model payloads.

The deployed source commit is now confirmed. To establish the remaining production trigger, use the supplied failing request ID. Correlate it with the safe application event: `operation:extract` or `audit`, `phase`, `finishReason`, `providerStatus`, `providerRequestId`, and schema issue paths/codes if present. If production is still running the old catch with no retained diagnostics, the historical cause may not be recoverable. New diagnostics require a separately approved deployment before they can explain a fresh production occurrence.

## Conclusion after deployment provenance confirmation

The deployment-to-source mapping is now supplied by the user, not inferred. At the confirmed commit, the exact reported message is emitted only by `structured()` after a successful upstream HTTP status. Its catch includes response-envelope JSON parsing, choice/finish/refusal checks, model-content JSON parsing and Zod validation (including thrown refinements). Both extraction and the independent factuality audit use it. The error signature does not distinguish those two calls.

For this request signature, the POST/method gate, Access/input/quota rejection paths, initial fetch failure/non-2xx response paths, schema-generation exceptions in the request-building expression, timeout branch, final API-response validation and a supported=false factuality verdict have different error codes or messages. They cannot explain this exact signature in the confirmed source. This is control-flow evidence; it does not supply the actual provider finish reason, refusal flag, response payload or validation path.

PR #7 implemented the diagnostics and consistency fixes and was subsequently merged. It did not deploy them. This provenance update changes the confidence of the source attribution, not the remaining uncertainty about the private response that triggered the catch. The synthetic reproductions already used the now-confirmed deployed commit. No weaker validator, guessed repair, automatic retry or automatic deployment is warranted by the additional metadata.
